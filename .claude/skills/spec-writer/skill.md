# Spec Writer — превращение брифа клиента в ТЗ для AI-агента

## Назначение

Берёт сырое, путаное описание задачи от клиента (бриф, голосовые расшифровки, переписку, «хочу чтобы бот делал вот это…») и превращает его в чёткий, структурированный документ Технического Задания, по которому можно начинать разработку AI-агента.

## Когда вызывать

- Пользователь прислал описание задачи и просит «оформить», «структурировать», «написать ТЗ», «сделать SPEC».
- Пользователь дал сырое ТЗ и просит привести его к стандартному виду.
- Пользователь говорит «вот что хочет клиент, нужно сделать техзадание».
- Пользователь вставляет бриф клиента и говорит «разбери и оформи».

Не вызывать, если задача — проанализировать уже готовое ТЗ, провести ревью или реализовать проект. Этот скилл только пишет ТЗ.

## Принципы

1. **Не додумывать.** Всё, что не сказано клиентом прямо, не выдумывать. Если информации не хватает — выносить в раздел «Уточняющие вопросы к клиенту» или помечать явно как `[ДОПУЩЕНИЕ: …]` с обоснованием.
2. **Структура важнее полноты.** Лучше честно пометить раздел «Не указано клиентом», чем заполнить его выдуманными деталями.
3. **Язык — язык клиента.** ТЗ пишется на русском, если клиент писал на русском. Термины клиента сохраняются.
4. **Сначала вопросы, потом файл.** Если критической информации не хватает (нет цели, нет описания результата) — задать вопросы ДО генерации файла. Если не хватает второстепенного — сгенерировать файл, включив вопросы внутрь.

## Алгоритм работы

1. Прочитай сырой текст задачи от пользователя.
2. Выдели из него: цель, входные данные, ожидаемый результат, ограничения, контекст клиента.
3. Для каждого факта определи источник:
   - явно сказано клиентом → используй как факт;
   - следует из контекста, но не сказано прямо → `[ДОПУЩЕНИЕ: …]`;
   - отсутствует и не следует из контекста → вынеси в «Уточняющие вопросы».
4. Если отсутствуют КРИТИЧЕСКИЕ поля (Цель или Ожидаемый результат) — задай пользователю уточняющие вопросы и остановись. Файл не создавать.
5. Иначе сгенерируй Markdown по шаблону ниже.
6. Сохрани результат в файл `docs/tz-[kebab-case-тема-клиента].md` и сообщи пользователю путь.

## Шаблон результата

```markdown
# ТЗ: [Название проекта]

> Дата составления: [YYYY-MM-DD]
> Источник: [краткое описание брифа клиента — например, «переписка в Telegram от 2026-07-20»]
> Статус: [Черновик | Согласовано с клиентом]

## 1. Цель и бизнес-задача

[Зачем клиенту этот AI-агент. Какую боль решает, какой процесс автоматизирует. 2–5 предложений. Если цель не указана явно — раздел «Уточняющие вопросы».]

## 2. Входные данные

Что есть у клиента на старте:
- **Данные:** [какие массивы, источники, форматы — базы, документы, API]
- **Инструменты:** [какие системы уже используются — CRM, мессенджеры, сайты]
- **Команда / контакты:** [кто вовлечён, кто заказчик, кто пользователь]
- **Бюджет и сроки:** [если упомянуты; иначе «Не указано»]

## 3. Ожидаемый результат

Что агент должен делать:
- [Конкретное действие 1 — измеримое]
- [Конкретное действие 2]
- [Конкретное действие 3]

**Критерии приёмки** (как поймём, что агент работает):
- [Критерий 1]
- [Критерий 2]

**Не входит в скоуп:**
- [Что точно НЕ делаем — чтобы зафиксировать границы]

## 4. Технические ограничения и стек

| Параметр | Значение |
|---|---|
| Платформа / рантайм | [Python / Node / … или «Не указано»] |
| LLM-провайдер | [OpenAI / Anthropic / open-source / «Не указано»] |
| Хостинг | [VPS / serverless / локально / «Не указано»] |
| Интеграции | [API-сервисы, которые нужно подключить] |
| Ограничения по данным | [персданные, NDA, локация хранения] |
| Язык интерфейса | [ru / en / …] |

> Если клиент не указал стек — таблица остаётся со значениями «Не указано». Не выдумывать технологии за клиента.

## 5. Уточняющие вопросы к клиенту

Сгруппируй по приоритету. Каждый вопрос — отдельный буллет, чтобы клиент мог отвечать по пунктам.

**Блок A — критично (без ответов нельзя начать разработку):**
- [ ] [Вопрос 1]
- [ ] [Вопрос 2]

**Блок B — важно (влияет на архитектуру):**
- [ ] [Вопрос 3]
- [ ] [Вопрос 4]

**Блок C — желательно (уточнения по UX/edge-cases):**
- [ ] [Вопрос 5]

- `[ДОПУЩЕНИЕ] …`
```

## Правила сохранения

- Путь: `docs/tz-[kebab-case-тема-клиента].md` в корне проекта пользователя (где лежит `claude.md` / `CLAUDE.md`).
- **Имя файла — только латиница в kebab-case.** Длина — до 5 слов. Тема проекта транслитерируется. Примеры: `docs/tz-cooking-researcher.md`, `docs/tz-telegram-support-bot.md`, `docs/tz-telegram-bot.md`.
- Перед записью проверь, что папка `docs/` существует; если нет — создай.
- Если файл с таким именем уже есть — добавь суффикс `-v2`, `-v3` и т.д., не перезаписывай молча.
- В конце ответа пользователю — **всегда** сообщи полный путь к сохранённому файлу.

## Чего НЕ делать

- Не писать ТЗ без раздела «Уточняющие вопросы», даже если кажется, что всё ясно.
- Не подставлять технологии, которых клиент не упоминал, даже если они кажутся «очевидными».
- Не сохранять файл, если отсутствует Цель или Ожидаемый результат — сначала задай вопросы.
- Не выводить готовое ТЗ только в чат, если правило сохранения не отменено пользователем явно.
- Не использовать кириллицу в имени файла.
